# サンプルテストをビルドして実行する

```bash
neoj test
neoj test src/main.cpp
neoj t                       # alias
```

`neoj test` は解法をコンパイルし、テストケースディレクトリにダウンロード済みのすべてのサンプルで実行し、出力を対応する `.out` ファイルと比べます。

## 実行前に

このコマンドには、`neoj.toml` と `[languages.<key>]` セクションを持つプロジェクト、そしてテストケースディレクトリに1つ以上の `*.in` ファイルが必要です。先にサンプルをダウンロードします(対話モードは、`*.in` ファイルなしで1セッションだけ実行できます)。

```bash
neoj init
neoj d https://atcoder.jp/contests/abc300/tasks/abc300_a
```

## 言語を設定する

`[languages.<key>]` セクションが1つの言語を記述します。キーは好きな名前でよく、`neoj` はメッセージとキャッシュのエントリに使います。

```toml
[test]
source = "src/main.cpp"

[languages.cpp]
source = "src/**/*.cpp"
compile = ["g++", "-std=c++23", "-O2", "-o", "{outfile}", "{source}"]
run = ["{outfile}"]
```

- `source` は、どのファイルがその言語に属するかを示すグロブ(またはグロブの一覧)です。`neoj test` はソースファイルをこれらのグロブに照合し、一致した1つの言語を使います。
- `compile` は省略できます。インタプリタ言語では省きます。たとえば `run = ["python3", "{source}"]` です。
- `run` は標準入力でテスト入力を受け取り、プロジェクトのルートから実行します。

引数はプログラムに直接渡されます。シェルは関与しないため、配列の中では引用符やリダイレクトが動きません。シェルが本当に必要なときは `["sh", "-c", "…"]` と書きます。

### プレースホルダー

| プレースホルダー | 値                                               |
| ---------------- | ------------------------------------------------ |
| `{source}`       | ソースファイルの絶対パス。                       |
| `{outfile}`      | ビルドされたプログラムの絶対パス。拡張子なし。   |
| `{outdir}`       | `{outfile}` などのビルド出力を置くディレクトリ。 |
| `{dir}`          | プロジェクトのルート。                           |
| `{testdir}`      | テストケースディレクトリの絶対パス。             |

`compile` は `{outfile}` か `{outdir}` を使う必要があります。ビルドしたプログラムを確認してキャッシュするためです。Windowsでは、`<outfile>.exe` というファイルが存在するとき、`{outfile}` はそのパスに解決されます。拡張子をコンパイラ自身が付けることがあるためです。

## ソースファイルを選ぶ

`neoj test` は、引数を渡したときは `[source]` 引数を、渡さないときは `test.source` を使います。パスは実在するファイルで、プロジェクトの中になければなりません。ここではグロブを受け付けません。そのファイルをすべての言語の `source` グロブに照合し、ちょうど1つの言語が一致しなければなりません。複数が一致するときは `--language` を渡します。

```bash
neoj test --language cpp
```

### ソースファイルに名前を付けて保存する

`[alias]` に短い名前を登録し、パスの代わりに渡します。

```toml
[alias]
main = "src/main.cpp"
old = "archive/2019/a.cpp"
```

```bash
neoj test main     # builds src/main.cpp
neoj t old         # builds archive/2019/a.cpp
```

対象はプロジェクトのルートから解決されるため、同じエイリアスがサブディレクトリからも使えます。同じ名前のファイルが存在してもエイリアスが優先されます(ファイルに届くのは `neoj test ./main` のときです)。エイリアスが別のエイリアスを指すことはできず、`test.source` は展開されません。存在しない名前は、定義済みのエイリアスとともに報告されます。

## 実行の流れ

1. ソースファイルとその言語を解決します。
2. キャッシュ済みのビルドがまだ有効でなければ、1度だけコンパイルします。
3. すべてのテストケースを実行します。既定では並列です。
4. 名前順で報告を表示します。完成した順に関係ありません。

進捗バーは標準エラーに描かれます。出力先がターミナルでないときや、`--no-progress` を渡したときは、バーを飛ばし、最終報告だけを書き込みます。

## 報告を読む

```text
✓ sample-1      45 ms    28 MiB  AC
✗ sample-2      37 ms    28 MiB  WA (line 2)
    Line │ Input
       1 │ 1 2
       2 │ 3

    Line │ Expected │ Output
       1 │ 3 7      │ 3 7
       2 │ 1        │ 1 8

    stderr:
      warning: 'x' is unused
? sample-3      36 ms    28 MiB  UNJUDGED (expected output missing)
    Line │ Input
       1 │ 4

    Line │ Output
       1 │ 42

3 case(s): 1 passed, 1 failed, 1 unjudged (68 ms; slowest 45 ms, peak 28 MiB).
```

| 判定       | 意味                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| `AC`       | 出力が一致しました。                                                              |
| `WA`       | 出力が異なります。すべての行が表示され、異なる行に色が付きます。                  |
| `TLE`      | 時間制限を超え、プログラムが停止されました。                                      |
| `MLE`      | ピークのメモリ使用量が制限を超えました(実行後に確認)。                            |
| `RE`       | プログラムが0以外の終了状態で終わった、終了させられた、または出力があふれました。 |
| `UNJUDGED` | `.out` ファイルがありません。プログラムは実行され、出力が表示されます。           |

各ケースの行には、名前のあとに実行時間とピークのメモリ使用量が入ります。メモリは直接の子プロセスに対して測り、プラットフォームが報告しないときは `? MiB` と表示します。最終行は、実行全体の所要時間、最も遅いケース、最も高いピークメモリを繰り返します。

`MLE` のケースが報告するのは超えた制限だけです。たとえば `MLE (> 1024 MiB)` です。メモリの列にすでに測定値が入っているためです。

どの失敗でも、それを生んだ入力、続いて期待する出力と実際の出力が表示されます。`.out` ファイルのないケースでは、プログラムの出力が代わりに表示されます。`-v` を付けると、合格したケースにも同じ表が付きます。

幅のあるターミナルでは、両方の出力が1つの表に並びます。幅のないターミナル、タブ、長い行では、見出しを保ったまま2つの表が縦に積まれます。

合格しなかったケースと次のケースの間には、空行が2行入ります。

## 対話問題をテストする

入力を一度にすべて読むのではなく、ジャッジとやり取りする問題があります。`neoj test --interactive`(または `-i`)は解法とインタラクタを同時に起動し、パイプでつなぎます。

```text
test/sample-1.in ──▶ interactor (path passed with {infile})
interactor stdout ──▶ solution stdin
solution stdout   ──▶ interactor stdin
```

インタラクタを `neoj.toml` に記述します。

```toml
[test.interactor]
source = "src/interactor.cpp"
run = ["{outfile}", "{infile}"]
```

- `source` は必須で、プロジェクトのルートからの単純なパスです。
- `compile` と `run` の既定は、`source` グロブがインタラクタのファイルに一致する `[languages.<key>]` のエントリです。C++のインタラクタなら、`{infile}` を受け取る `run` だけをここに書けば足ります。
- `{infile}` はケースの `.in` ファイルのパスに展開されます。`run` だけで使え、標準入力は解法の出力側にあります。
- 判定を決めるのはインタラクタです。終了ステータス `0` が `AC` で、それ以外は `WA` です。stderrの最初の空でない行が `WA (...)` の理由になります。
- 解法自身の失敗が優先されます。`TLE`、`MLE`、`RE`、出力の上限は、インタラクタが答えを受け付けたはずでも報告されます。
- `.out` ファイルは無視されます。ディレクトリに `*.in` ファイルが1つもないときは、`{infile}` なしで1セッションが実行されます。入力を自分で作るインタラクタのための仕様です。
- 両方のプログラムは、書き込む行をすべてフラッシュする必要があります。さもないと、相手はいつまでも待ちます。C++では `std::endl` か `std::cout.flush()` を、Pythonでは `flush=True` か `sys.stdout.flush()` を使います。
- `test.interactor.timeout`(既定は15秒)がセッション全体に掛かります。解法自身の制限は引き続き `test.timeout` / `-t` です。

報告では、入力と出力の表がやり取りの記録に置き換わります。

```text
✗ sample-1     41 ms    12 MiB  WA (wrong answer: 3 != 7)
    interactive:
      J> 1 2
      S> 3
      J> 5
      S> 8
    interactor stderr:
      wrong answer: 3 != 7
```

`J>` がインタラクタから解法への行、`S>` が解法からインタラクタへの行です。失敗では記録が表示され、`-v` では `AC` でも表示されます。表示する行数は `test.display_lines` が制限します。

## 複数の正しい答えを許す問題を判定する

複数の正しい出力を認める問題があります。`neoj test --judge`(または `-j`)は、解法の終了後にチェッカーを実行し、出力が認められるかをチェッカーに決めさせます。

```text
test/sample-1.in ──▶ checker (path passed with {infile}, optional)
solution stdout   ──▶ checker stdin
```

チェッカーを `neoj.toml` に記述します。

```toml
[test.judge]
source = "src/checker.cpp"
run = ["{outfile}", "{infile}"]
```

- `source` は必須で、プロジェクトのルートからの単純なパスです。
- `compile` と `run` の既定は、`source` グロブがチェッカーのファイルに一致する `[languages.<key>]` のエントリです。C++のチェッカーなら、`{infile}` を受け取る `run` だけをここに書けば足ります。
- 解法の標準出力がチェッカーの標準入力になります。`{infile}` はケースの `.in` のパスに展開され、省略できます。チェッカーが出力だけを検証するときは外します。
- 判定を決めるのはチェッカーです。終了ステータス `0` が `AC` で、それ以外は `WA` です。stderrの最初の空でない行が `WA (...)` の理由になります。
- 解法自身の失敗が優先されます。`TLE`、`MLE`、`RE`、出力の上限は、チェッカーが答えを受け付けたはずでも報告されます。
- `.out` ファイルは無視され、ディレクトリには `*.in` ファイルが最低1つ必要です。
- `test.judge.timeout`(既定は10秒)がチェッカーに掛かります。メモリ制限はありません。

報告には、入力と解法の出力に続いて、チェッカーのstderrと解法のstderrが表示されます。期待値と実際の出力の比較表はありません。

```text
✗ sample-1     41 ms    12 MiB  WA (wrong values)
    Line │ Input
       1 │ 1 2 3

    Line │ Output
       1 │ 3 1 1

    judge stderr:
      wrong values
```

## 行に番号を付け、長い行を切り詰める

`Line` の列がすべての表の行に番号を付けます。既定で有効です。外すには `test.show_line_numbers = false` を設定するか、`--no-show-line-numbers` を渡します。

`test.display_lines`(既定は `30`)より長いブロックは、`… N more line(s)` で切り詰められます。1つの大きなケースが報告をあふれさせないためです。比較表は例外で、常にすべての行を並べます。制限が掛かるのは、入力、プログラムの出力、合格したケースの詳細表です。

```toml
[test]
show_line_numbers = true
display_lines = 30
```

## プログラムの標準エラーを表示する

プログラムの標準エラーは、何かを書いた各ケースのあとに、判定に関係なく表示されます。

```text
✓ sample-1      12 ms    28 MiB  AC
    stderr:
      warning: 'x' is unused
```

行は書かれたとおりに再現されます。色は付かず、切り詰められず、プログラムが少なくとも1バイト書いたときだけ出ます。表示する量は `test.show_stderr` で選びます。

```toml
[test]
show_stderr = "failure"   # "always" (default), "failure", or "never"
```

- `"always"` は、すべてのケースの標準エラーを表示します。
- `"failure"` は、合格しなかったケースにだけ表示します。
- `"never"` は、決して表示しません。

`neoj test --show-stderr failure` は、1回の実行だけ設定を上書きします。

## 比較を緩める

1回の実行だけ比較を緩めるオプションが2つあります。

```bash
neoj test -S    # ignore whitespace at the end of each line
neoj test -N    # ignore newlines at the end of the output
```

`test.ignore_trailing_space` か `test.ignore_trailing_newline` を設定すると、その動作が既定になります。行の中の空白は常に意味を持ち、CRLFは自動的に正規化されます。

## 浮動小数点の出力を判定する

小さな数値の誤差を認める問題では、`-e` を渡します。許容差が有効になり、指数が大きさを選びます。

```bash
neoj test -e       # 10^-6 (the default)
neoj test -e 9     # 10^-9
```

トークンは、次の式が成り立つとき一致します。

```text
|actual - expected| <= 10^-exponent * max(1, |expected|)
```

そのため、同じ規則がゼロ近くの絶対誤差と、大きな値に対する相対誤差の両方を受け入れます。数値トークンは書き方が違っても数として比べます(`1e-7` と `0.0000001` は一致し、`1` と `1.0` も一致します)。`NaN`、`Infinity`、16進表記はテキストとして比べます。

`-e` を付けると、出力全体がASCIIの空白で分割されるため、改行や空白の連続は問題にならず、トークンの順序と値だけが問題になります。`-S` と `-N` には追加の効果がありません。

`-e` に引数がないときに使う既定の指数は、`test.error` で変えられます。

```toml
[test]
error = 9
```

許容差を外れた数値の差は、両方の値とともに報告されます。

```text
✗ sample-1     45 ms    28 MiB  WA (line 1: 0 vs 0.000002)
```

このオプションは、判定を決めるのがインタラクタやチェッカーのため、`--interactive` と `--judge` では無視されます。どちらかのモードと組み合わせると、`neoj` が警告を表示します。

## 選んだケースを実行する

```bash
neoj test -f sample-1 sample-3
```

名前は `.in` を除いたファイル名で、完全に一致する必要があります。存在しない名前は、使えるケースとともに報告されます。

## ケースを手で加える

サンプルが確かめたいケースを網羅しないときは、ターミナルから作ります。

```bash
neoj handmade
```

入力を打ち、空行で終えます。続いて期待する出力を打ち、同じように終えます。ファイルが書き込まれるのは、両方のブロックが完成したあとです。[テストケースを手で作る](create-handmade-tests.md)を参照してください。

## 制限

- `test.timeout` の既定は10秒です。`neoj test -t 2` か `languages.<key>.timeout` で変わります。対話モードでは解法のプロセスに掛かり、セッション全体は `test.interactor.timeout`(既定は15秒)が制限します。ジャッジモードでは解法に掛かり、チェッカーは `test.judge.timeout`(既定は10秒)が制限します。
- `test.memory` の既定は1024MiBです。制限は、プログラムのプロセスが終了したあとのピークの常駐メモリから判定されます。子プロセスを起動するプログラムでは、直接の子だけが測定対象です。対話モードとジャッジモードでは解法だけに適用され、インタラクタとチェッカーには適用されません。
- 標準出力と標準エラーには、それぞれ8MiBの上限があります。上限を超えたプログラムは停止され、`RE` として報告されます。対話モードでは上限が両方のプログラムに掛かり、ジャッジモードでは解法とチェッカーのstderrに掛かります。

## コンパイル済みのプログラムをキャッシュする

`test.cache = true` を設定すると、ビルドを再利用します。

```toml
[test]
cache = true

[languages.cpp]
cache_files = ["src/**/*.hpp"]
```

キャッシュのキーは、言語、コンパイルコマンド、ソースの中身、`cache_files`、プラットフォームをカバーします。キーごとに `.neoj/build/` の下に専用のディレクトリができ、古いエントリは残るため、2つの解法を行き来しても速く済みます。`neoj prune` はキャッシュ済みのビルドをすべて削除し、`neoj prune --dry-run` は先に件数と大きさを報告します。

`neoj test --cache` と `neoj test --no-cache` は、1回の実行だけ設定を上書きします。`--no-cache` は、終了時にその実行のビルドディレクトリを削除します。

## 終了ステータス

すべてのケースが合格すると `0`、1つでも失敗すると `2`、`neoj` がコンパイルや設定の読み取りに失敗すると `1` です。
