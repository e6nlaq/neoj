# プラットフォームと統合

`neoj` はすべての競技サイトを**プラットフォーム**として扱います。プラットフォームとは、ログイン、セッションの確認、問題の読み取り方を知っている、名前付きの統合です。コマンドは一度だけ書かれ、どのプラットフォームでも同じように動きます。

## コマンドの形

プラットフォームは、名前、表示名、そして3つの操作(ログイン、保存済みセッションがまだ有効かの確認、そもそも認証情報が存在するかの報告)とともに登録されます。CLIはその登録表を直接使います。

- `neoj login <platform>` は、登録済みのプラットフォームごとに1つのサブコマンドを公開します。
- `neoj logout --service <name...>` は名前を登録表に照らして検証します。
- `neoj status` は登録済みのすべてのプラットフォームを順に見ます。そのため、出力は保存済みセッションの有無に関係なく安定します。

このため、プラットフォームを追加してもCLIの形は変わりません。コマンドは同じままで、登録表が伸びるだけです。

## プラットフォームを選ぶ

`login` と `logout` はプラットフォーム名を受け取ります。`download` は代わりにURLを受け取るため、URLをどの統合が扱うかはパーサが決めます。パーサは対応プラットフォームに属さないURLを、うまい具合に取得しようとする代わりに拒否します。

登録済みのプラットフォームはAtCoderとyukicoderです。認証の方法は異なります。

- AtCoderはブラウザのセッションcookie(`REVEL_SESSION`)を再利用します。
- yukicoderは、ブラウザのデバイスフローで取得する提出専用のCLIトークンか、`Bearer` 認証情報として保存するアカウントのAPIキーのどちらかを使います。

どの認証情報も、`neoj` が保存する前に検証されます。

## 用語

このドキュメントでは**プラットフォーム**と書きます。CLIはその語を **service** と混ぜて使う場所があります。`logout` は `--service` を受け取り、`status` は自分をserviceの言葉で説明します。どちらも同じ登録表のエントリを指します。

## 分担

プラットフォームのコードはHTTP要求、HTMLの解析、URLの検証を受け持ちます。コマンドは引数の処理と表示を受け持ちます。この分担を分けておくことで、新しいプラットフォームが、既存のファイル、テンプレート、認証情報の処理に触れずに再利用できます。
